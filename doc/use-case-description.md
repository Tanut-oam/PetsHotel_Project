## UC-01 สมัครสมาชิก (Register)

| หัวข้อ | รายละเอียด |
|---|---|
| **Actor หลัก** | ผู้เยี่ยมชม (Guest) |
| **คำอธิบาย** | ผู้เยี่ยมชมสร้างบัญชีลูกค้าเพื่อใช้จองห้องพัก |
| **เงื่อนไขก่อนเริ่ม** | ยังไม่ได้เข้าสู่ระบบ |
| **เงื่อนไขหลังจบ** | มีบัญชีใหม่บทบาท `CUSTOMER` สถานะใช้งาน และรหัสผ่านถูกเข้ารหัสด้วย BCrypt |

**ขั้นตอนหลัก**
1. ผู้เยี่ยมชมเปิดหน้าสมัครสมาชิก
2. กรอกชื่อ นามสกุล อีเมล เบอร์โทร รหัสผ่าน และยืนยันรหัสผ่าน
3. ระบบตรวจความถูกต้องของข้อมูล
4. ระบบแปลงอีเมลเป็นตัวพิมพ์เล็กและตรวจว่ายังไม่ถูกใช้
5. ระบบบันทึกบัญชีบทบาท `CUSTOMER` พร้อมรหัสผ่านที่เข้ารหัสแล้ว
6. ระบบพาไปหน้าเข้าสู่ระบบพร้อมข้อความว่าสมัครสำเร็จ

**กรณีผิดปกติ**
- 3a. อีเมลผิดรูปแบบ, เบอร์โทรไม่ขึ้นต้นด้วย 0 หรือไม่ใช่ 9–10 หลัก, รหัสผ่านสั้นกว่า 8 ตัว → แสดงข้อผิดพลาดที่ช่องนั้น
- 3b. รหัสผ่านกับยืนยันรหัสผ่านไม่ตรงกัน → แสดง "รหัสผ่านไม่ตรงกัน"
- 4a. อีเมลถูกใช้แล้ว → แสดง "อีเมลนี้ถูกใช้สมัครแล้ว" ที่ช่องอีเมล

**โค้ดที่เกี่ยวข้อง:** `AuthController`, `AuthServiceImpl.register()`, `RegisterRequest`

## UC-02 เข้าสู่ระบบ (Log In)

| หัวข้อ | รายละเอียด |
|---|---|
| **Actor หลัก** | ลูกค้า, พนักงาน, ผู้ดูแลระบบ |
| **คำอธิบาย** | ผู้ใช้ยืนยันตัวตนด้วยอีเมลและรหัสผ่าน แล้วระบบพาไปหน้าที่เหมาะกับบทบาท |
| **เงื่อนไขก่อนเริ่ม** | มีบัญชีที่ยังใช้งานอยู่ |
| **เงื่อนไขหลังจบ** | ผู้ใช้เข้าสู่ระบบ ระบบจำการเข้าสู่ระบบไว้ 30 วันจนกว่าจะออกจากระบบ |

**ขั้นตอนหลัก**
1. ผู้ใช้เปิดหน้าเข้าสู่ระบบ แล้วกรอกอีเมลและรหัสผ่าน
2. ระบบค้นหาบัญชีด้วยอีเมลตัวพิมพ์เล็ก และเทียบรหัสผ่านกับ BCrypt hash
3. ระบบตรวจว่าบัญชียังใช้งานอยู่
4. ระบบพาไปหน้าตามบทบาท: ผู้ดูแลระบบ → `/admin`, พนักงาน → `/admin/bookings`, ลูกค้า → หน้าแรก

**ทางเลือก**
- 4a. ผู้ใช้ถูกพามาหน้าเข้าสู่ระบบเพราะเปิดหน้าที่ต้องล็อกอินก่อน → หลังเข้าสู่ระบบแล้วกลับไปหน้าที่ตั้งใจเปิด

**กรณีผิดปกติ**
- 2a. อีเมลหรือรหัสผ่านไม่ถูกต้อง → แจ้งข้อผิดพลาด
- 3a. บัญชีถูกระงับ (`active = false`) → เข้าสู่ระบบไม่ได้

**โค้ดที่เกี่ยวข้อง:** `SecurityConfig`, `CustomUserDetailsService`, `RoleBasedLoginSuccessHandler`

## UC-03 ค้นหาห้องว่าง (Search Available Rooms)

| หัวข้อ | รายละเอียด |
|---|---|
| **Actor หลัก** | ผู้เยี่ยมชม, ลูกค้า |
| **คำอธิบาย** | ผู้ใช้ระบุช่วงวันเข้าพักและจำนวนสัตว์เลี้ยง ระบบแสดงห้องที่ว่างทั้งห้องตลอดช่วงนั้นและรับสัตว์ได้ตามจำนวน |
| **เงื่อนไขก่อนเริ่ม** | ไม่ต้องเข้าสู่ระบบ |
| **เงื่อนไขหลังจบ** | ผู้ใช้เห็นรายการห้องว่าง และกดจองห้องที่เลือกต่อได้ (UC-05) |

**ขั้นตอนหลัก**
1. ผู้ใช้เปิดหน้าค้นหาห้องว่าง แล้วเลือกวันเช็กอิน วันเช็กเอาต์ และจำนวนสัตว์เลี้ยง
2. ระบบตรวจว่ากรอกครบ วันเช็กเอาต์อยู่หลังวันเช็กอิน และจำนวนสัตว์อย่างน้อย 1 ตัว
3. ระบบดึงห้องที่สถานะ `ACTIVE` ทั้งหมด
4. ระบบคัดเฉพาะห้องที่รับสัตว์ได้ไม่น้อยกว่าจำนวนที่ระบุ และไม่มีการจองสถานะ `PENDING`, `CONFIRMED` หรือ `CHECKED_IN` ทับช่วงวันที่ (หนึ่งห้องต่อหนึ่งการจอง)
5. ระบบแสดงรายการห้องว่างพร้อมราคาต่อตัวต่อคืน และปุ่ม "จองห้องนี้"
6. ผู้ใช้กด "จองห้องนี้" ระบบพาไปฟอร์มจองพร้อมห้องและวันที่ที่เลือก (ไป UC-05)

**ทางเลือก**
- 6a. ผู้ใช้ยังไม่ได้เข้าสู่ระบบ → ระบบพาไปหน้าเข้าสู่ระบบ แล้วกลับมาที่ฟอร์มจองพร้อมห้องและวันที่เดิม (UC-02 ทางเลือก 4a)
- 1a. ระบบภายนอกเรียกผ่าน REST API `GET /api/rooms/available` ได้ผลเป็น JSON ด้วยกฎเดียวกัน
- 1b. ค้นหาห้องแบบแบ่งหน้าและเรียงลำดับผ่าน `GET /api/rooms/search` (keyword, minCapacity, maxPrice, page, size, sort)

**กรณีผิดปกติ**
- 2a. กรอกไม่ครบ → แจ้ง "กรุณากรอกวันที่และจำนวนสัตว์เลี้ยงให้ครบถ้วน"
- 2b. วันเช็กเอาต์ไม่อยู่หลังวันเช็กอิน → แจ้ง "วันที่ Check-out ต้องอยู่หลังวันที่ Check-in"
- 2c. จำนวนสัตว์น้อยกว่า 1 → แจ้ง "จำนวนสัตว์เลี้ยงต้องอย่างน้อย 1 ตัว"
- 5a. ไม่มีห้องว่างในช่วงที่เลือก → แสดง "ไม่มีห้องว่างในช่วงวันที่เลือก"
- REST API: ข้อมูลไม่ถูกต้องตอบ 400 พร้อม `ErrorResponse`

**โค้ดที่เกี่ยวข้อง:** `AvailabilityController`, `AvailabilityRestController`, `AvailabilityServiceImpl.findAvailableRooms()`, `BookingRepository.existsOverlappingBooking()`, `AvailabilityMapper`, `RoomSearchServiceImpl`

## UC-04 จัดการสัตว์เลี้ยง

| หัวข้อ | รายละเอียด |
|---|---|
| **Actor หลัก** | ลูกค้า |
| **Actor รอง** | — |
| **คำอธิบาย** | ลูกค้าเพิ่ม แก้ไข หรือนำสัตว์เลี้ยงของตนออกจากรายการที่ใช้งาน และอาจแนบรูปภาพสัตว์เลี้ยง |
| **เงื่อนไขก่อนเริ่ม (Pre-condition)** | ลูกค้าเข้าสู่ระบบ และบัญชียังใช้งานอยู่ |
| **เงื่อนไขหลังจบ (Post-condition)** | ข้อมูลสัตว์เลี้ยงถูกบันทึกหรือแก้ไขตามคำขอ หากนำออกจากรายการ ระบบเปลี่ยน `active` เป็น `false` โดยไม่ลบข้อมูลออกจากฐานข้อมูล |
| **Include / Extend** | — |

**ขั้นตอนหลัก (Main Flow)**
1. ลูกค้าเปิดหน้าสัตว์เลี้ยงของฉัน
2. ระบบแสดงสัตว์เลี้ยงที่ยังใช้งานอยู่และเป็นของลูกค้าคนนั้น
3. ลูกค้าเลือกเพิ่มสัตว์เลี้ยงและกรอกชื่อ ประเภท และข้อมูลอื่นที่ต้องการ
4. ลูกค้ากดบันทึก
5. ระบบตรวจสอบข้อมูลที่กรอก และผูกสัตว์เลี้ยงกับบัญชีของลูกค้า
6. ระบบบันทึกสัตว์เลี้ยงใหม่โดยกำหนด `active = true`
7. ระบบกลับไปหน้ารายการและแสดงข้อความว่าบันทึกสำเร็จ

**ทางเลือก (Alternative Flow)**
- 3a. ลูกค้าแนบรูปภาพ → หลังบันทึกข้อมูลสัตว์เลี้ยง ระบบจัดเก็บรูปภาพและเชื่อมรูปกับสัตว์เลี้ยง
- 3b. ลูกค้าเลือกแก้ไขสัตว์เลี้ยงที่มีอยู่ → ระบบตรวจสอบว่าเป็นเจ้าของ แล้วบันทึกข้อมูลที่แก้ไข
- 3c. ลูกค้าเลือกนำสัตว์เลี้ยงออกจากรายการ → ระบบตรวจสอบว่าเป็นเจ้าของ แล้วเปลี่ยน `active` เป็น `false` สัตว์เลี้ยงจึงไม่ปรากฏในรายการที่ใช้งาน

**กรณีผิดปกติ (Exception Flow)**
- 5a. ข้อมูลที่กรอกไม่ผ่านการตรวจสอบ เช่น ไม่ระบุชื่อหรือประเภท อายุเป็นค่าติดลบ หรือน้ำหนักไม่มากกว่าศูนย์ → ระบบแจ้งให้ตรวจสอบข้อมูลและไม่บันทึกคำขอนั้น
- 3b-1. ไม่พบสัตว์เลี้ยง หรือสัตว์เลี้ยงไม่ได้เป็นของลูกค้า → ระบบไม่อนุญาตให้แก้ไขและตอบว่าไม่พบข้อมูล
- 3c-1. ไม่พบสัตว์เลี้ยง หรือสัตว์เลี้ยงไม่ได้เป็นของลูกค้า → ระบบไม่เปลี่ยนสถานะและตอบว่าไม่พบข้อมูล
- 3a-1. อัปโหลดรูปภาพไม่สำเร็จ → ระบบแจ้งข้อผิดพลาด โดยข้อมูลสัตว์เลี้ยงที่บันทึกหรือแก้ไขก่อนหน้านั้นยังคงอยู่

**โค้ดที่เกี่ยวข้อง:** `PetPageController`, `PetServiceImpl.createPet()`, `PetServiceImpl.updatePet()`, `PetServiceImpl.deactivatePet()`, `PetServiceImpl.updatePetImage()`, `CreatePetRequest`, `UpdatePetRequest`

## UC-05 จองห้องพัก

| หัวข้อ | รายละเอียด |
|---|---|
| **Actor หลัก** | ลูกค้า |
| **Actor รอง** | — |
| **คำอธิบาย** | ลูกค้าเลือกห้อง ช่วงวันเข้าพัก และสัตว์เลี้ยง เพื่อสร้างการจองที่รอพนักงานยืนยัน |
| **เงื่อนไขก่อนเริ่ม (Pre-condition)** | ลูกค้าเข้าสู่ระบบแล้ว และมีสัตว์เลี้ยงที่ยังใช้งานอยู่อย่างน้อย 1 ตัว |
| **เงื่อนไขหลังจบ (Post-condition)** | มีการจองใหม่สถานะ `PENDING` และสถานะชำระเงิน `UNPAID` บันทึกราคาไว้ ณ เวลาที่จอง |
| **Include / Extend** | include: ตรวจสอบห้องว่าง, คำนวณราคา · extend: เลือกบริการเสริม, ใช้โปรโมชัน |

**ขั้นตอนหลัก (Main Flow)**
1. ลูกค้าเลือกห้องจากหน้ารายการห้องหรือผลค้นหาห้องว่าง
2. ลูกค้าเลือกวันเช็กอินและเช็กเอาต์
3. ระบบแสดงฟอร์มจอง พร้อมรายการสัตว์เลี้ยงของลูกค้า (ปิดตัวที่มีการจองซ้อนช่วงเดียวกัน)
4. ลูกค้าเลือกสัตว์เลี้ยง
5. ระบบคำนวณและแสดงราคาโดยประมาณ
6. ลูกค้ากดยืนยันการจอง
7. ระบบตรวจสอบห้องว่าง ความจุ และสัตว์ที่จองซ้อน
8. ระบบคำนวณราคาอีกครั้งและบันทึกการจองเป็นสถานะ `PENDING`
9. ระบบแสดงหน้ารายละเอียดการจอง

**ทางเลือก (Alternative Flow)**
- 4a. ลูกค้าเลือกบริการเสริมให้สัตว์แต่ละตัว → ระบบรวมค่าบริการในราคา
- 4b. ลูกค้าเลือกโปรโมชัน → ระบบตรวจว่าโปรโมชันใช้ได้ ณ วันที่จอง แล้วหักส่วนลด

**กรณีผิดปกติ (Exception Flow)**
- 7a. ห้องไม่ว่างในช่วงที่เลือก → แจ้ง "ห้องไม่ว่าง" และไม่บันทึกการจอง
- 7b. จำนวนสัตว์เกินความจุห้อง → แจ้งข้อผิดพลาด
- 7c. สัตว์มีการจองซ้อนในช่วงเดียวกัน → แจ้งชื่อสัตว์และช่วงวันที่ที่ซ้อน
- 4b-1. โปรโมชันหมดอายุหรือยังไม่เริ่ม → แจ้งข้อผิดพลาดและไม่บันทึกการจอง

**โค้ดที่เกี่ยวข้อง:** `BookingController`, `BookingServiceImpl.createBooking()`, `AvailabilityService.checkRoomAvailable()`, `PricingService.calculate()`

| **คำอธิบาย** | ผู้ใช้ยกเลิกการจองที่ยังไม่ชำระเงินและอยู่ในสถานะรอยืนยันหรือยืนยันแล้ว |

| **เงื่อนไขหลังจบ (Post-condition)** | การจองเปลี่ยนเป็น `CANCELLED` โดยยังเก็บข้อมูลไว้ในฐานข้อมูล และไม่นับรายการนี้เป็นการสงวนห้องหรือสัตว์เลี้ยงในช่วงวันที่เดิม |
| **Include / Extend** | — |

**ขั้นตอนหลัก (Main Flow)**

1. ลูกค้าเปิดหน้าการจองของฉันหรือหน้ารายละเอียดการจอง
2. ระบบแสดงปุ่มยกเลิกสำหรับรายการที่มีสถานะ `PENDING` หรือ `CONFIRMED` และสถานะชำระเงิน `UNPAID`
3. ลูกค้ากดยกเลิกและยืนยันในหน้าต่างยืนยัน
4. ระบบตรวจบัญชีผู้ใช้และตรวจว่าลูกค้าเป็นเจ้าของการจอง
5. ระบบโหลดและล็อกการจอง แล้วตรวจว่ายังไม่ชำระเงิน
6. ระบบเลือก State ตามสถานะปัจจุบัน และเรียก `cancel(booking)` ผ่าน `PendingState` หรือ `ConfirmedState`
7. ระบบเปลี่ยนสถานะเป็น `CANCELLED` และบันทึกการจอง
8. ระบบกลับไปหน้ารายละเอียดการจอง พร้อมข้อความ “ยกเลิกการจองเรียบร้อยแล้ว”

**ทางเลือก (Alternative Flow)**

- 3a. ลูกค้าปิดหรือปฏิเสธหน้าต่างยืนยัน → ระบบไม่ส่งคำขอยกเลิก และการจองยังมีสถานะเดิม
- 1a. พนักงานหรือผู้ดูแลระบบเปิดหน้าจัดการการจอง `/admin/bookings` → เลือกรายการและยืนยันการยกเลิก ระบบตรวจสิทธิ์ `STAFF` / `ADMIN` แล้วใช้กฎสถานะและการชำระเงินเดียวกัน เมื่อสำเร็จกลับไปหน้าจัดการการจองพร้อมข้อความแจ้งผล

**กรณีผิดปกติ (Exception Flow)**

- 4a. ยังไม่เข้าสู่ระบบ → ต้องเข้าสู่ระบบก่อนทำรายการ
- 4b. บัญชีถูกระงับ → ระบบปฏิเสธการทำรายการ
- 4c. ลูกค้าพยายามยกเลิกการจองของผู้อื่น → ระบบไม่อนุญาต โดยเส้นทางเว็บตอบว่าไม่พบข้อมูล และไม่เปลี่ยนสถานะ
- 5a. ไม่พบการจอง → ระบบแจ้งว่าไม่พบข้อมูล
- 5b. การจองมีสถานะชำระเงิน `PAID` → ระบบปฏิเสธการยกเลิก และไม่เปลี่ยนข้อมูลการชำระเงิน
- 6a. การจองอยู่ในสถานะ `CHECKED_IN`, `CHECKED_OUT` หรือ `CANCELLED` → State ปฏิเสธการยกเลิกด้วย `IllegalStateException` และไม่บันทึกสถานะใหม่

**กฎการทำงานเพิ่มเติม**

- ยกเลิกได้เฉพาะการจองสถานะ `PENDING` หรือ `CONFIRMED` ที่ยังไม่ชำระเงิน
- การยกเลิกเปลี่ยนสถานะการจอง โดยไม่ลบ Booking, BookingPet หรือรายการบริการเสริม
- การตรวจห้องและสัตว์ที่ติดจองนับเฉพาะ `PENDING`, `CONFIRMED` และ `CHECKED_IN` จึงไม่นับการจองที่เป็น `CANCELLED`
- ระบบตรวจเงื่อนไขซ้ำที่ Service แม้หน้าเว็บจะแสดงปุ่มเฉพาะรายการที่ยกเลิกได้แล้ว
- REST API ใช้ `POST /api/bookings/{id}/cancel` และตอบ `409 Conflict` เมื่อสถานะหรือการชำระเงินไม่อนุญาตให้ยกเลิก

**โค้ดที่เกี่ยวข้อง:** `BookingController.cancelBooking()`, `AdminBookingController.performAction()`, `BookingRestController.cancelBooking()`, `BookingServiceImpl.cancelBooking()`, `PendingState.cancel()`, `ConfirmedState.cancel()`, `BookingRepository.findByIdForUpdate()`, `AvailabilityServiceImpl`

## UC-09 ยืนยันรับชำระเงิน (Confirm Payment)

| หัวข้อ | รายละเอียด |
|---|---|
| **Actor หลัก** | พนักงาน (ผู้ดูแลระบบทำได้เช่นกัน) |
| **คำอธิบาย** | พนักงานบันทึกว่าลูกค้าชำระเงินเต็มจำนวนแล้ว และระบบออกใบเสร็จ |

| **เงื่อนไขหลังจบ** | การจองมีสถานะชำระเงิน `PAID` บันทึกยอดและเวลารับเงิน และมีใบเสร็จ 1 ใบ |

**ขั้นตอนหลัก**
1. พนักงานเปิดหน้าจัดการการจอง แล้วกด "ยืนยันรับชำระเงิน"
2. ระบบล็อกแถวการจอง (`findByIdForUpdate`) เพื่อกันการยืนยันซ้ำพร้อมกัน
3. ระบบตรวจสถานะการจองและยอดเงิน
4. ระบบบันทึก `payment_status = PAID`, ยอดที่ชำระเท่ากับยอดรวมของการจอง และเวลาที่รับเงิน
5. ระบบออกใบเสร็จเลขที่ `REC-<UUID>` โดยใช้ราคาที่บันทึกไว้ตอนจอง ไม่คำนวณราคาใหม่
6. ระบบแสดงข้อความสำเร็จ

**ทางเลือก**
- 2a. การจองชำระเงินแล้ว → คืนใบเสร็จเดิม ไม่บันทึกเวลารับเงินใหม่

**กรณีผิดปกติ**
- 3a. การจองเป็น `PENDING` หรือ `CANCELLED` → แจ้งว่ายังรับชำระเงินไม่ได้
- 3b. ยอดรวมของการจองไม่ถูกต้อง → แจ้งข้อผิดพลาด
- 5a. ออกใบเสร็จไม่สำเร็จ → ย้อนการบันทึกการชำระเงินทั้งหมด (อยู่ใน transaction เดียวกัน)

| **เงื่อนไขหลังจบ (Post-condition)** | มีรายงานการดูแลของสัตว์ในการจองสำหรับวันที่เลือก พร้อมข้อมูลผู้บันทึก โดยสัตว์หนึ่งรายการในการจองมีรายงานได้ไม่เกินหนึ่งฉบับต่อวัน |
| **Include / Extend** | — |

**ขั้นตอนหลัก (Main Flow)**
1. พนักงานเปิดหน้ารายงานการดูแลและเลือกการจองกับสัตว์เลี้ยง
2. ระบบแสดงข้อมูลสัตว์เลี้ยงและรายงานที่เคยบันทึกไว้
3. พนักงานเลือกเขียนรายงานและระบุวันที่รายงาน
4. พนักงานกรอกข้อมูลการให้อาหาร การเดินเล่น การดูแลความสะอาด อารมณ์ สุขภาพ และหมายเหตุที่เกี่ยวข้อง
5. พนักงานกดบันทึก
6. ระบบตรวจสอบว่าผู้บันทึกเป็นพนักงานหรือผู้ดูแลระบบ และการจองอยู่ในสถานะ `CHECKED_IN` หรือ `CHECKED_OUT`
7. ระบบตรวจสอบว่าวันที่รายงานอยู่ในช่วงวันเช็กอินถึงวันเช็กเอาต์ และยังไม่มีรายงานของสัตว์ในการจองรายการนี้ในวันเดียวกัน
8. ระบบบันทึกรายงานพร้อมผู้บันทึก แล้วแสดงข้อความว่าบันทึกสำเร็จ

**ทางเลือก (Alternative Flow)**
- 3a. พนักงานเลือกรายงานที่บันทึกไว้แล้วและกดแก้ไข → ระบบแสดงข้อมูลเดิม พนักงานแก้ข้อมูลแล้วบันทึก โดยระบบตรวจสอบวันที่ สัตว์ในการจอง และรายงานที่อาจซ้ำอีกครั้ง
- 1a. พนักงานค้นหาการจองจากหมายเลขการจอง ชื่อหรืออีเมลเจ้าของ หรือชื่อสัตว์เลี้ยง และกรองการจองที่มีรายงานตามวันที่ ก่อนเลือกรายการที่ต้องการ

**กรณีผิดปกติ (Exception Flow)**
- 6a. ผู้ใช้ไม่ใช่พนักงานหรือผู้ดูแลระบบ → ระบบปฏิเสธการบันทึกหรือแก้ไขรายงาน
- 6b. ไม่พบสัตว์ในการจอง หรือการจองไม่ได้อยู่ในสถานะ `CHECKED_IN` หรือ `CHECKED_OUT` → ระบบไม่บันทึกรายงาน
- 7a. วันที่รายงานอยู่นอกช่วงเข้าพัก → ระบบแจ้งให้ตรวจสอบวันที่และไม่บันทึก
- 7b. มีรายงานของสัตว์ในการจองรายการนี้ในวันที่เลือกแล้ว → ระบบแจ้งว่ามีรายงานอยู่แล้วและไม่สร้างรายงานซ้ำ
- 4a. ข้อมูลไม่ผ่านการตรวจสอบ เช่น ระยะเวลาเดินเล่นติดลบ → ระบบแจ้งให้ตรวจสอบข้อมูลและไม่บันทึก

**โค้ดที่เกี่ยวข้อง:** `AdminCareReportPageController`, `DailyCareReportServiceImpl.createReport()`, `DailyCareReportServiceImpl.updateReport()`, `CreateDailyCareReportRequest`, `UpdateDailyCareReportRequest`, `DailyCareReport`

## UC-13 จัดการโปรโมชัน (Manage Promotions)

| หัวข้อ | รายละเอียด |
|---|---|

| **คำอธิบาย** | ผู้ดูแลระบบดูรายการ เพิ่ม แก้ไข และเปิดหรือปิดใช้งานโปรโมชัน |
| **เงื่อนไขก่อนเริ่ม** | เข้าสู่ระบบด้วยบทบาท `ADMIN` |
| **เงื่อนไขหลังจบ** | ข้อมูลโปรโมชันถูกบันทึกตามที่ระบุ โปรโมชันจะใช้กับการจองได้เมื่อเปิดใช้งานและอยู่ในช่วงวันที่กำหนด |

**ขั้นตอนหลัก (เพิ่มโปรโมชัน)**

1. ผู้ดูแลระบบเปิดหน้าจัดการโปรโมชัน `/admin/promotions`
2. ระบบแสดงรายการโปรโมชันทั้งหมด พร้อมส่วนลด วันหมดอายุ และสถานะเปิดใช้งาน
3. ผู้ดูแลระบบกด “เพิ่มโปรโมชัน”
4. กรอกชื่อ เลือกประเภทส่วนลด ระบุมูลค่าส่วนลด วันเริ่มต้น วันสิ้นสุด และสถานะเปิดใช้งาน โดยสามารถกรอกรายละเอียดและจำนวนคืนขั้นต่ำเพิ่มเติมได้ แล้วกด “บันทึก”
5. ระบบตรวจข้อมูล โดยชื่อห้ามว่าง มูลค่าส่วนลดต้องมากกว่า 0 หากเป็นเปอร์เซ็นต์ต้องไม่เกิน 100 วันสิ้นสุดต้องไม่ก่อนวันเริ่มต้น และจำนวนคืนขั้นต่ำหากระบุต้องเป็นจำนวนเต็มตั้งแต่ 1
6. ระบบตัดช่องว่างหัวท้ายของชื่อและรายละเอียด แล้วบันทึกโปรโมชัน โดยรายละเอียดว่างบันทึกเป็น `NULL` และจำนวนคืนขั้นต่ำที่เว้นว่างหมายถึงไม่กำหนดขั้นต่ำ
7. ระบบกลับไปหน้ารายการพร้อมข้อความ “เพิ่มโปรโมชันสำเร็จ”

**ทางเลือก**

- A1. ค้นหารายการ → ผู้ดูแลระบบค้นหาตามชื่อและกรองสถานะเปิดใช้หรือปิดใช้ ระบบแสดงรายการที่ตรงกับตัวกรอง
- A2. แก้ไขโปรโมชัน → กด “แก้ไข” ระบบแสดงข้อมูลเดิมในฟอร์ม ผู้ดูแลระบบแก้ข้อมูลแล้วบันทึก ระบบตรวจข้อมูลและแสดงข้อความ “แก้ไขโปรโมชันสำเร็จ”
- A3. ปิดใช้งานโปรโมชัน → เปิดฟอร์มแก้ไข เอาเครื่องหมาย “เปิดใช้โปรโมชัน” ออก แล้วบันทึก ระบบกำหนด `active = false` โดยไม่ลบข้อมูล
- A4. เปิดใช้งานอีกครั้ง → เปิดฟอร์มแก้ไข เลือก “เปิดใช้โปรโมชัน” แล้วบันทึก โปรโมชันจะใช้ได้เมื่ออยู่ในช่วงวันที่กำหนดด้วย
- A5. ยกเลิกการกรอก → กด “ยกเลิก” เพื่อปิดฟอร์มโดยไม่บันทึก

**กรณีผิดปกติ**

- 5a. ชื่อว่าง ไม่เลือกประเภทส่วนลด หรือไม่กรอกข้อมูลที่จำเป็น → แสดงข้อผิดพลาดในฟอร์มและไม่บันทึก
- 5b. มูลค่าส่วนลดเป็น 0 หรือติดลบ → แสดงข้อผิดพลาดและไม่บันทึก
- 5c. ส่วนลดแบบเปอร์เซ็นต์มากกว่า 100 → แสดงข้อผิดพลาดและไม่บันทึก
- 5d. มูลค่าส่วนลดมีจำนวนเต็มเกิน 8 หลักหรือทศนิยมเกิน 2 ตำแหน่ง → แสดงข้อผิดพลาดและไม่บันทึก
- 5e. ไม่ระบุวันเริ่มต้นหรือวันสิ้นสุด หรือวันสิ้นสุดก่อนวันเริ่มต้น → แสดงข้อผิดพลาดและไม่บันทึก โดยอนุญาตให้วันเริ่มต้นและวันสิ้นสุดเป็นวันเดียวกันได้
- 5f. จำนวนคืนขั้นต่ำเป็น 0 ติดลบ หรือไม่ใช่จำนวนเต็ม → แสดงข้อผิดพลาดในฟอร์มและไม่บันทึก
- A2-1. ไม่พบโปรโมชันที่ต้องการแก้ไข → ระบบกลับไปหน้ารายการพร้อมข้อความแจ้งข้อผิดพลาด

7. ระบบกลับไปหน้ารายการพร้อมข้อความ “เพิ่มบริการเสริมสำเร็จ”

**ทางเลือก**

- A1. ค้นหารายการ → ผู้ดูแลระบบค้นหาตามชื่อและกรองสถานะเปิดใช้หรือปิดใช้ ระบบแสดงรายการที่ตรงกับตัวกรอง
- A2. แก้ไขบริการเสริม → กด “แก้ไข” ระบบแสดงข้อมูลเดิมในฟอร์ม ผู้ดูแลระบบแก้ข้อมูลแล้วบันทึก ระบบตรวจข้อมูลและแสดงข้อความ “แก้ไขบริการเสริมสำเร็จ”
- A3. ปิดใช้งานบริการ → เปิดฟอร์มแก้ไข เอาเครื่องหมาย “เปิดใช้บริการ” ออก แล้วบันทึก ระบบกำหนด `active = false` โดยไม่ลบข้อมูล และไม่อนุญาตให้เลือกบริการนั้นในการจองใหม่
- A4. เปิดใช้งานอีกครั้ง → เปิดฟอร์มแก้ไข เลือก “เปิดใช้บริการ” แล้วบันทึก
- A5. ยกเลิกการกรอก → กด “ยกเลิก” เพื่อปิดฟอร์มโดยไม่บันทึก

**กรณีผิดปกติ**

- 5a. ชื่อว่างหรือไม่ระบุราคา → แสดงข้อผิดพลาดในฟอร์มและไม่บันทึก
- 5b. ราคาติดลบ → แสดงข้อผิดพลาดและไม่บันทึก
- 5c. ราคามีจำนวนเต็มเกิน 8 หลักหรือทศนิยมเกิน 2 ตำแหน่ง → แสดงข้อผิดพลาดและไม่บันทึก
- A2-1. ไม่พบบริการที่ต้องการแก้ไข → ระบบกลับไปหน้ารายการพร้อมข้อความแจ้งข้อผิดพลาด

**กฎการทำงานเพิ่มเติม**

- การแก้ราคาบริการไม่เปลี่ยน `unit_price` และ `total_price` ของรายการบริการที่บันทึกในการจองเดิมโดยอัตโนมัติ
- การปิดใช้งานบริการยังคงเก็บข้อมูลบริการและรายการที่เคยจองไว้

**โค้ดที่เกี่ยวข้อง:** `AdminExtraServicePageController`, `ExtraServiceServiceImpl`, `ExtraServiceRequest`, `ExtraServiceMapper`, `ExtraServiceRepository`, `BookingServiceImpl`, `SecurityConfig`

## UC-15 จัดการสมาชิก (Manage Users)

| หัวข้อ | รายละเอียด |
|---|---|
| **Actor หลัก** | ผู้ดูแลระบบ |
| **คำอธิบาย** | ผู้ดูแลระบบค้นหา เรียงลำดับ และแก้ไขข้อมูล บทบาท และสถานะของสมาชิก |
| **เงื่อนไขก่อนเริ่ม** | เข้าสู่ระบบด้วยบทบาท `ADMIN` |
| **เงื่อนไขหลังจบ** | ข้อมูลสมาชิกถูกบันทึก สมาชิกที่ถูกระงับเข้าสู่ระบบไม่ได้ |

**ขั้นตอนหลัก**
1. ผู้ดูแลระบบเปิดหน้าสมาชิก ระบบแสดงรายชื่อทั้งหมด
2. (ไม่บังคับ) ค้นหาด้วยชื่อ อีเมล หรือเบอร์โทร และเลือกการเรียงลำดับ
3. กด "แก้ไข" ที่สมาชิกที่ต้องการ
4. แก้ชื่อ นามสกุล อีเมล เบอร์โทร บทบาท หรือสถานะบัญชี
5. ระบบตรวจข้อมูล แปลงอีเมลเป็นตัวพิมพ์เล็ก และตรวจอีเมลซ้ำ
6. ระบบบันทึกและกลับไปหน้ารายชื่อพร้อมข้อความสำเร็จ

**กรณีผิดปกติ**
- 5a. รูปแบบอีเมลหรือเบอร์โทรไม่ถูกต้อง → กลับไปหน้าแก้ไขพร้อมข้อผิดพลาด
- 5b. อีเมลถูกใช้โดยบัญชีอื่น → แจ้ง "อีเมลนี้ถูกใช้แล้ว"
- 5c. ผู้ดูแลระบบพยายามเปลี่ยนบทบาท ระงับ หรือเปลี่ยนอีเมลของ**ตัวเอง** → ปฏิเสธ เพื่อกันการล็อกตัวเองออกจากระบบ

**โค้ดที่เกี่ยวข้อง:** `AdminUserPageController`, `UserServiceImpl`, `UpdateUserRequest`

## UC-16 ดู Dashboard รายได้ (View Revenue Dashboard)

| หัวข้อ | รายละเอียด |
|---|---|
| **Actor หลัก** | ผู้ดูแลระบบ |
| **คำอธิบาย** | ผู้ดูแลระบบดูภาพรวมการจอง ยอดรับเงินรายเดือนและรายปี รวมถึงรายละเอียดรายการรับเงินและใบเสร็จ |
| **เงื่อนไขก่อนเริ่ม** | เข้าสู่ระบบด้วยบทบาท `ADMIN` |
| **เงื่อนไขหลังจบ** | ระบบแสดงข้อมูลภาพรวมและยอดรับเงินตามปีที่เลือก โดยไม่เปลี่ยนข้อมูลการจองหรือการชำระเงิน |

**ขั้นตอนหลัก**

1. ผู้ดูแลระบบเปิดหน้า Dashboard `/admin`
2. ระบบใช้ปีปัจจุบันเป็นปีเริ่มต้น และแสดงยอดรับเงินเดือนนี้ จำนวนรายการจองที่มีช่วงเข้าพักในเดือนนี้ ห้องว่างคืนนี้ และสัตว์ที่กำลังเข้าพัก
3. ระบบแสดงการจองล่าสุดไม่เกิน 5 รายการ พร้อมเลขที่การจอง ลูกค้า สัตว์เลี้ยง ห้อง และสถานะ
4. ผู้ดูแลระบบระบุปี ค.ศ. แล้วกด “ดูยอดเงิน”
5. ระบบตรวจว่าปีอยู่ระหว่าง 1–9999 และรวมยอดจากใบเสร็จของการจองที่ยืนยันรับเงินแล้ว โดยจัดเดือนตามวันที่รับเงิน
6. ระบบแสดงยอดรับเงินครบ 12 เดือนและยอดรวมทั้งปีของปีที่เลือก
7. ผู้ดูแลระบบกดชื่อเดือน ระบบเปิดหน้าต่างรายการรับเงินของเดือนนั้น พร้อมจำนวนรายการ ยอดรวม เลขที่การจอง ลูกค้า วันที่รับเงิน และยอดรับเงิน
8. ผู้ดูแลระบบกด “ดูรายละเอียด” ของรายการ ระบบแสดงสัตว์เลี้ยง ห้อง วันเข้าพัก วันออก ค่าห้อง ค่าบริการเสริม ค่าใช้จ่ายเพิ่มเติม ส่วนลด และเลขที่ใบเสร็จ

**ทางเลือก**

- A1. ไม่เปลี่ยนปี → ดูยอดรายเดือนและรายปีของปีปัจจุบันได้ทันที
- A2. เปลี่ยนปี → ระบุปีใหม่แล้วกด “ดูยอดเงิน” ระบบปรับส่วนรายงานรายเดือนและรายปีตามปีที่เลือก
- A3. ดูใบเสร็จ → กด “ดูใบเสร็จ” ในรายละเอียดรายการ ระบบเปิดใบเสร็จในแท็บใหม่
- A4. ย่อรายละเอียด → กด “ย่อรายละเอียด” เพื่อซ่อนรายละเอียดของรายการนั้น
- A5. ปิดรายการของเดือน → กด “ปิด” เพื่อกลับมาดูตารางยอดรายเดือน
- A6. เดือนที่ไม่มีรายการรับเงิน → แสดงยอด 0.00 บาท และเมื่อเปิดเดือนนั้น แสดงข้อความ “เดือนนี้ยังไม่มีรายการที่ยืนยันรับเงินแล้ว”
- A7. ยังไม่มีการจอง → ตารางการจองล่าสุดแสดงข้อความ “ยังไม่มีรายการจอง”

**กรณีผิดปกติ**

- 5a. ส่งปีนอกช่วง 1–9999 → ระบบปฏิเสธคำขอด้วย HTTP 400 โดยช่องกรอกปีบนหน้าจอกำหนดช่วงเดียวกันไว้ด้วย
- A2-1. โหลดรายงานของปีที่เลือกไม่สำเร็จ → แสดงข้อความ “โหลดรายงานไม่สำเร็จ กรุณาลองอีกครั้ง หากหมดเวลาเข้าสู่ระบบให้เข้าสู่ระบบใหม่”

**กฎการทำงานเพิ่มเติม**

- ยอดรับเงินรวมจาก `Receipt.totalAmount` เฉพาะรายการที่มีการจองเกี่ยวข้อง มี `paymentStatus = PAID` และมี `paidAt`
- การจัดยอดเข้าเดือนและปีใช้ `Booking.paidAt` ไม่ใช่วันสร้างการจอง วันเข้าพัก หรือวันออกใบเสร็จ
- เดือนที่ไม่มีรายได้ยังแสดงในตาราง โดยมียอด 0.00 บาท ยอดรวมทั้งปีเป็นผลรวมของทั้ง 12 เดือน
- รายการรับเงินภายในแต่ละเดือนเรียงตาม `paidAt` จากเก่าไปใหม่
- การเลือกปีเปลี่ยนเฉพาะส่วนรายงานรายเดือนและรายปี ส่วนการ์ด “ยอดรับเงินเดือนนี้” และ “การจองเข้าพักเดือนนี้” ยังคงอ้างอิงเดือนปัจจุบัน
- จำนวนการจองเข้าพักเดือนนี้นับหนึ่งครั้งต่อหนึ่งการจองที่มีอย่างน้อยหนึ่งคืนพักอยู่ในเดือนปัจจุบัน รวมการพักข้ามเดือน โดยไม่นับรายการสถานะ `CANCELLED`
- เกณฑ์ช่วงพักคือวันเช็กอินอยู่ก่อนวันแรกของเดือนถัดไป และวันเช็กเอาต์อยู่หลังวันแรกของเดือนปัจจุบัน โดยไม่นับวันเช็กเอาต์เป็นคืนพัก
- นับรวมรายการรอยืนยัน (`PENDING`) และไม่ใช้ `createdAt` หรือจำนวนสัตว์เป็นเกณฑ์นับ รายการที่ไม่มีวันเข้าพักครบหรือวันเช็กเอาต์ไม่อยู่หลังวันเช็กอินจะไม่นับ
- จำนวนสัตว์ที่กำลังเข้าพักนับสัตว์ในการจองสถานะ `CHECKED_IN`
- การจองล่าสุดเรียงตาม `createdAt` จากใหม่ไปเก่า และใช้ `id` จากมากไปน้อยเมื่อวันเวลาสร้างเท่ากัน โดยไม่ได้ตัดรายการที่ยกเลิกออก
